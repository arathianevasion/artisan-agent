# Triage

Sort incoming tickets in the Product chat. This replaces upstream `triage`: same roles, grilling and discard mechanism, but in version one **nothing is applied until the Artisan approves it**, and nothing reaches `ready-for-agent` without that approval.

Follow `${CLAUDE_PLUGIN_ROOT}/ARTISAN.md` for every item you put in front of the Artisan: lead with the problem, arrive with a recommendation, show the reasoning and the strongest rejected alternative. Use `GLOSSARY.md` vocabulary and respect `docs/adr/`. Label strings come from `docs/agents/triage-labels.md`; tracker commands from `docs/agents/issue-tracker.md`.

Every comment or ticket posted during triage **must** start with:

```
> *This was generated by AI during triage.*
```

## Roles and outcomes

Category roles: `bug`, `enhancement`. State roles: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. Our label `deferred` marks a deferral. Every triaged ticket carries one category and one state.

The Artisan's outcomes for a ticket:

- **Do**: it goes ahead. Write the agent brief and apply `ready-for-agent`.
- **Defer**: not now, see below.
- **Discard**: reject it, see below.
- **Take it myself**: `ready-for-human`, same brief structure, with a note why it can't be delegated.

`needs-info` (post the triage notes template) and `needs-triage` (leave in the queue) are ways to move an item along, not outcomes. A ticket marked `in-run` is never re-triaged, edited or relabelled here.

## What goes through triage

Tickets from agents, findings or other people go through triage. **A ticket the Artisan wrote or approved skips it** (the front door files those straight to `ready-for-agent`). Don't list or touch:

- tickets already `ready-for-agent` or `ready-for-human`, or `in-run`;
- tickets authored by the Artisan (compare the author to the Artisan's identity, found the way `docs/agents/issue-tracker.md` says; on a local-markdown tracker make no `gh` call at all) that don't start with the triage disclaimer or an agent-filed marker and aren't labelled `needs-triage`.

An agent files with `needs-triage`, so that label (or no label from someone other than the Artisan) is what makes a ticket triage work. An explicitly named ticket is triaged whoever wrote it, except that if it is the Artisan's own, say it normally skips triage and ask once whether they want it triaged anyway.

## Showing what needs attention

List, oldest first: unlabelled tickets from others, `needs-triage`, and `needs-info` with reporter activity since the last notes. Then do the gathering below for each item and present **two queues**. Controversy decides the queue and the order, never whether the Artisan sees an item.

### 1. Uncontroversial queue first

Items where none of the seven criteria applies (and no "Always ask" item in `PRODUCT_STANDARDS.md` or `CODING_STANDARDS.md` applies, at project, team or individual level). Show each as one line batch the Artisan can scan:

> #52 Fix typo in the install doc. **Recommend: Do.** Criterion: **none**. Why: meets the brief, fixes a defect, nothing to reverse.

The Artisan approves each recommendation, or moves the item to `needs-triage` (they disagree: it is controversial after all). Moving one to `needs-triage`, or ruling a different outcome than recommended, is a **miss** (below). Nothing is applied until approved; approving a batch is fine ("approve all except #54").

### 2. Controversial queue second

Each item names the criterion that applies by number, for example "criterion 3: new dependency", and carries your recommendation and the reasoning. Take them one at a time, highest-leverage first. Ask for the ruling: Do, Defer, Discard or take it myself. When in doubt, an item is controversial.

## Gathering context for an item

1. Read the whole ticket (body, comments, labels, author, dates) and prior triage notes; don't re-ask resolved questions. Explore the codebase with the glossary, respecting ADRs.
2. **Redundancy**: search for an existing implementation by domain concept and report where you looked. If found, it is an already-built request: close with a comment only, never write `.out-of-scope/`.
3. **Prior rejection**: read `.out-of-scope/*.md` and compare **every new ticket** against earlier rejections by concept. On a match, flag it against that file with its reason and ask: confirm (append the ticket to "Prior requests" and close), reconsider (update or delete the file; normal triage) or distinct (normal triage). A flagged item is always controversial: criterion 1 (it contradicts a recorded decision).
4. **Verify the claim** before grilling: reproduce a bug, check a PR does what it says. Report confirmed, failed, or insufficient detail (a strong `needs-info` signal).
5. **Grill if needed.** If the item needs shaping, call the Skill tool for `grilling` and `domain-modeling`.

## Applying an approved outcome

Only after the Artisan approves the item's outcome.

### Do / take it myself

Post an agent brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)); apply `ready-for-agent` (or `ready-for-human` with the reason it can't be delegated).

### Discard (upstream's mechanism, kept)

- **Rejected enhancement**: write or extend `.out-of-scope/<concept>.md` with a lasting reason (see [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md); a durable reason, not "too busy", which is a deferral), post a closing comment linking to it, label `wontfix` and close.
- **Bug rejected**: close with a polite comment explaining why, label `wontfix`.
- **Already built**: close with a comment pointing to where it lives, label `wontfix`. Do not write `.out-of-scope/`.

### Defer

Not now, and the ticket stays open.

1. Propose a **return condition** and get it approved with the deferral. Exactly one of:
   - **a date**;
   - **an event recorded as native blocking**: add the blocking ticket as a native dependency (`docs/agents/issue-tracker.md`, "Blocking") so the deferred ticket is blocked by it;
   - **next review**: default **30 days** from today (use `deferral review` in `.artisan-agent/config.yml` if set).
2. Add the `deferred` label, remove `needs-triage`, keep the ticket open.
3. Post a comment with the reason and, as its own line in exactly one of these forms (the backlog review and `scripts/deferred-due.sh` read it):

```
Return condition: date YYYY-MM-DD
Return condition: next review on YYYY-MM-DD
Return condition: blocked-by #12 #15
```

A deferred ticket doesn't come back through triage; the backlog review surfaces it when the condition is met. When it returns, remove `deferred`.

## Recording a miss

A **miss** is an "uncontroversial" recommendation the Artisan reversed: they moved it to `needs-triage` or ruled a different outcome. The retro counts misses and raises each with the criterion that should have caught it.

Record each one at once, after the Artisan reverses it, with:

```bash
${CLAUDE_PLUGIN_ROOT}/skills/triage/scripts/record-miss.sh <ticket> <criterion 1-7|new> <recommended> <ruled> "<reason>"
```

- Choose the criterion that **should have** made the item controversial, by number. Use `new` when no existing criterion fits (the retro treats it as a candidate for a new "Always ask" item).
- Records are lines in `.artisan-agent/triage/misses.jsonl` in the project's main checkout (project state, not per-run, because triage runs in the Product chat outside any run). Each has `ts`, `ticket`, `recommended`, `ruled`, `criterion_that_should_have_caught_it`, `reason` and `run_id` (from `ARTISAN_RUN_ID` when a run is open, else `null`). The folder contains its own `.gitignore`, so records stay out of git. The retro reads every record newer than the last retro.
- Also add a line "Triage miss: recommended X, ruled Y (criterion N)" to the ticket's comment when you apply the ruling, so the tracker shows it too.

Don't record a miss when the Artisan only asks for more information, or approves the recommendation.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1

**What we still need from you (@reporter):**

- question 1
```

Capture everything resolved during grilling under "established so far". Questions must be specific and actionable.

## Resuming

If prior triage notes exist, read them, check whether the reporter answered, and present an updated picture. Don't re-ask resolved questions.
